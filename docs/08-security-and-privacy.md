# 08 · 认证、安全与隐私

## 1. 目标、模式与边界

本文件约束 `REQ-03`、`REQ-04`、`REQ-22`、`REQ-25`、`REQ-27` 的实现。当前仓库仍是欢迎页，下述内容是实施与验收契约，不代表认证、数据库或安全检查已经上线。字段与状态以 [04 · 数据模型](04-data-model.md) 为准，方法和错误以 [05 · 服务接口](05-api-contracts.md) 为准，发布路径见 [09 · 部署与运行](09-deployment-and-operations.md)。

| 模式 | 身份与数据边界 | 可以承诺的行为 |
| --- | --- | --- |
| M1 `demo` | 演示身份、人工示例数据和当前浏览器 IndexedDB | 完整业务操作、浏览器内保存、实际计算与文件下载；不提供真实身份验证或用户间安全隔离 |
| M2 `live` | Supabase Auth、受保护数据库、服务端授权 | 真实身份、多人共享、跨设备恢复、受控提交和审计；必须通过本文件的验证 |

GitHub Pages 能运行浏览器 JavaScript，也能调用外部认证和数据 API。它没有内置业务后端，不等于技术上不能实现注册。GitHub 官方同时明确告诫：Pages 不应用于发送密码等敏感交易；因此本设计将 Pages 默认用于 M1，M2 的完整应用部署到适合真实认证的托管环境并接入 Supabase。外部认证并不自动构成平台政策豁免。依据：[GitHub Pages 概述](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)、[Pages 使用限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)。

默认真实认证选用**邮箱一次性验证码 OTP**，不建设本站密码体系。这个选择用于降低长期密码管理负担，不表示 OTP 不属于敏感认证凭据，也不表示它绕过了 Pages 的告诫。Pages 上的外部 OAuth 仅是完成适用性核对后的非敏感试运行选项，不是 M2 必须额外实现的功能，也不作为默认已获 GitHub 认可的生产路线。

## 2. 真实注册、登录与建档

### 2.1 默认流程

1. 认证页说明当前为真实模式、邮箱由认证服务处理、业务数据保存位置，并展示站点隐私告知入口。
2. 用户选择注册或登录并输入邮箱。注册允许为新邮箱建立 Auth 身份；登录按已有身份处理。调用 Supabase 的 `signInWithOtp`，两种入口明确设置 `shouldCreateUser`，不依赖 SDK 默认值。
3. 用户输入邮件中的验证码，调用 `verifyOtp`。只有服务端验证成功才建立真实会话；任何前端固定验证码或倒计时都不能代替验证。
4. 首次验证后，以幂等的受控服务端流程创建 `profiles` 和 `user_roles`。`user_id` 取自当前 Auth 身份，初始 `role=participant`、`state=pending_consent`，不接受客户端提供的权限或账户状态。
5. 首次建档展示昵称、评价员代号说明和站点告知。用户明确接受后记录 `profiles.consent_version`、`consented_at`，由受控 RPC 将状态改为 `active`；未接受时只开放建档、本人状态、退出等必要入口。
6. 进入具体实验前，展示该实验发布快照中的告知版本与保留策略。只有本人可接受该任务的告知；`AssignmentService.acceptNotice`（`api_accept_assignment_notice`）将 `assignments.privacy_notice_version`、`consented_at` 绑定到 `config_version_id`。服务端在保存和提交时验证这一条件，不能仅以“打开过说明页”代替接受。

Supabase 的 OTP 和 Magic Link 共用邮件实现，默认调用可能发送链接；实施时必须把邮件模板配置为展示 `{{ .Token }}`，并验收实际收到数字验证码。首次自动注册与已有用户登录的行为应分别测试。依据：[Passwordless email sign-in](https://supabase.com/docs/guides/auth/auth-email-passwordless)。

### 2.2 验证码与失败状态

本设计默认将验证码有效期配置为 `10` 分钟，重发按钮至少冷却 `60` 秒；它们是待实施的应用配置，不冒称服务当前默认值。最终有效期、发送和验证限速由 Auth 服务端执行。前端倒计时只辅助交互，不能作为抗滥用措施。

必须处理发送失败、发送限流、验证码错误、验证码过期、服务暂不可用、用户取消和重复验证。界面保留可重试的邮箱输入，不保存验证码；公开提示尽量不暴露某个邮箱是否已注册。日志不得记录验证码、完整认证响应、访问令牌、刷新令牌或邮件内的认证链接。

M2 使用自定义 SMTP。Supabase 默认发信服务只适合试验，存在收件人限制、可变化的低发送限额且无投递 SLA，不能作为面向真实评价员的发信方案。发信服务、域名验证、发送限制和失败告警的配置属于上线前提。依据：[Send emails with custom SMTP](https://supabase.com/docs/guides/auth/auth-smtp)。

本版本没有本站密码重置功能；邮箱 OTP 用户通过重新验证登录。更换联系邮箱、丢失邮箱或身份争议由站点负责人按受控流程处理，不能允许输入旧邮箱就替换账号归属。邀请邮件、短信和社交登录不是默认 M2 的交付范围。

## 3. 会话与浏览器存储

### 3.1 会话配置

`live` 的 Supabase SDK 使用专用 `storageKey` 和 `sessionStorage` 存储认证会话。键名必须包含应用、模式和 Supabase 项目标识，例如 `questionnaire:live:<project-ref>:auth:v1`；不得与演示身份复用。开启 SDK 会话恢复与令牌刷新时，必须显式传入该存储适配器，不能无意落回默认的 `localStorage`。

这使同一标签页刷新后可恢复登录；新设备需重新验证。`sessionStorage` 按源和标签页划分，可能随浏览器恢复会话而恢复，因此不能承诺“关闭页面就已从服务端撤销所有令牌”。它仍可被同源 JavaScript 读取，不能替代 XSS 防护。不同路径和不同 `storageKey` 只避免数据碰撞，不构成安全隔离；M2 优先使用独立、受控的站点源。依据：[Supabase 客户端初始化](https://supabase.com/docs/reference/javascript/initializing)、[MDN sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)。

认证状态变化后必须重新读取本人账户状态和角色。正常退出明确使用当前会话范围，清除本标签页会话、内存中的用户资料、答卷和分析数据；若服务端注销失败，说明本机已退出但远端撤销未确认，不误报“所有设备均已退出”。访问令牌在到期前可能仍有效，因此停用不能只依赖退出或令牌过期。依据：[Supabase signOut](https://supabase.com/docs/reference/javascript/auth-signout)。

### 3.2 业务数据只在服务端持久化

| 数据 | `demo` | `live` |
| --- | --- | --- |
| 演示身份 | 独立 `sessionStorage` 键 | 不使用 |
| Auth 会话 | 不生成真实令牌 | 仅 SDK 专用 `sessionStorage` |
| 实验、任务、草稿、答卷、分析 | IndexedDB 中的演示数据 | 服务端持久化；页面只保留必要内存状态 |
| 尚未保存的输入 | 内存，保存成功后进入 IndexedDB | 仅当前页面内存 |
| 管理员主动下载的文件 | 标明演示 | 经授权后下载到用户本机，不作为应用缓存 |

`live` 禁止把真实草稿、提交、文字反馈或分析输入写入 `localStorage`、IndexedDB、`sessionStorage`、Cache Storage 或 Service Worker 离线缓存。网络层不得把业务响应纳入持久缓存，查询缓存只在内存存在，退出、换账户和切换模式时清空。认证会话是上一节限定的存储例外。

断网时保留页面内存输入，显示“尚未保存，刷新或关闭可能丢失”，允许用户主动复制内容。恢复联网后重新读取版本，经用户确认处理冲突，再保存；不建立后台离线提交队列。只有取得服务端成功回执才显示已保存或已提交。`live` 的失败不能触发 `demo` 适配器，也不能以本地成功动画替代服务端结果。

## 4. 角色、账户状态与数据授权

### 4.1 权限来源

业务角色只取自受保护的 `user_roles`，账户状态只取自 `profiles`。每次业务 RPC 和受保护读取均检查当前 `auth.uid()`、账户状态与角色；不依赖前端菜单、浏览器存储、可变 `user_metadata` 或旧 JWT 中的业务角色。Supabase 的 `authenticated` 只代表认证后的数据库访问角色，不等于本站 `admin`。官方亦明确不应将用户可编辑的 `user_metadata` 用于授权。依据：[Supabase Users](https://supabase.com/docs/guides/auth/users)。

`pending_consent` 不能读取实验或写答卷；`disabled` 不能发起新的实验、答卷、分析或导出读写。本人状态查询、适用状态下的建档以及已核验本人的删除申请属于单独授权的账户生命周期入口，不由此开放实验内容。停用事务提交之后开始的业务请求即使携带尚未过期的 JWT，也必须被拒绝；对当前页面已下载内容不能承诺远程收回。恢复账户、角色维护和停用均通过可信流程处理，并使受影响实验的 `data_revision` 更新，按 [04](04-data-model.md) 标记旧分析过时。

| 操作 | 评价员 `participant` | 管理员 `admin` |
| --- | --- | --- |
| 读取站内资料 | 本人必要资料 | 受控评价员名单与管理所需字段 |
| 查看实验 | 本人获分配的参与端投影 | 站点内完整配置和管理状态 |
| 接受实验告知 | 只能接受自己的任务 | 如参与评价，也只能接受自己的任务 |
| 保存与提交 | 本人任务、允许的状态与时间内 | 仅对显式分配给自己的任务操作，不代填他人答卷 |
| 阅读他人答案、分析、导出 | 拒绝 | 管理范围内允许并审计 |
| 发布、分配、退回、关闭、停用 | 拒绝 | 通过受控 RPC 执行 |
| 授予管理员或修改角色表 | 拒绝 | 普通前端同样拒绝；交由可信维护流程 |

第一次管理员授权由项目所有者在可信管理环境对已验证、已完成建档的真实 UUID 执行，留下操作记录。不得根据“首个注册用户”、邮箱后缀、表单角色选项或公开邀请码自动授予管理员。必须验证仍有可用管理账号，并记录误停用后的受信恢复方法。

### 4.2 事务 RPC、RLS 与安全函数

业务创建、修改、提交、导入、状态转换、告知接受和审计写入全部经有授权检查的事务 RPC。认证提供方自身的 OTP、会话和注销操作仍使用 Auth API；它们不是绕过业务 RPC 的例外。浏览器不取得业务基表的直接 `INSERT`、`UPDATE`、`DELETE` 权限，不得直接修改角色、已发布配置或提交历史。

数据库必须同时设置最小权限的 schema/table grants 与 RLS，不能把“已启用 RLS”当成完整授权证明。服务函数遵循以下要求：

1. 每个入口显式验证 `auth.uid()`，从服务端读取当前账户状态和角色，再按该操作的契约验证目标实验、任务归属、告知、时间窗、版本及字段。采集时间窗适用于答卷保存、提交、退回及任务恢复，不阻止按状态机合法执行的关闭、归档、分配或撤销。客户端自报 `user_id` 不能决定操作主体。
2. 能用调用者权限完成的函数优先使用 `security invoker`。需要受权写入的 `security definer` 函数使用最小权限所有者，固定 `search_path`；推荐空路径，并对引用对象使用完整 schema 名。
3. 撤销 `PUBLIC`、`anon` 和其他不需要角色的函数执行权限；对每个公开业务 RPC 显式授予所需角色。设置未来新函数的默认权限，避免增加函数时重新开放匿名执行。
4. `security definer` 可能绕过调用者的 RLS，必须在函数内部检查归属和返回字段。固定 `search_path`、只授予 `authenticated` 都不能代替这些检查。
5. 同一事务完成校验、锁定、业务写入、版本更新、成功审计和幂等记录；采用 [04](04-data-model.md) 的锁顺序。任何步骤失败均不得残留半份导入或半次提交。若将数据库异常转换成 `Result.error`，必须先回滚该操作，不能捕获异常后返回错误却提交已经发生的部分写入。
6. SQL 使用受控参数和确定的查询结构，不拼接用户输入执行 SQL。未知字段、越界评分、重复 ID、跨实验引用、旧版本和非法状态转换均由服务端拒绝。
7. 成功幂等结果再次返回前也重新验证当前读取权限；账户被停用后不能靠旧幂等键读取结果。

Supabase 官方分别说明了 RLS 的 grants 边界、受权函数的 `search_path` 和默认执行权限风险。实施必须覆盖真实数据库的允许与拒绝测试。依据：[Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security)、[Database functions](https://supabase.com/docs/guides/database/functions)。

### 4.3 返回投影与发布不可变性

评价员接口在服务端只返回作答必需字段。`admin_name`、管理员身份、其他人的任务、评分和统计结果不得发送到参与端；`display_sample_names=false` 时，参与端也不能获得隐藏的 `display_name`。不能先下载完整管理 JSON，再靠 CSS 隐藏或前端删字段。

`experiment_versions` 的已发布配置、`privacy_notice_version` 和 `retention_policy` 都是不可变发布快照。隐私告知和保留策略来自站点受控设置，不接受任意 Excel/JSON 导入覆盖。调整题目、样品、量程或已发布期限应复制为新实验；不能用改写快照的方式重新解释旧答案。正常业务不覆盖历史提交；经核验的删除请求和到期清理是另外的受控数据处置流程，必须留下最小处理记录。

## 5. 密钥、输入和审计

### 5.1 配置与密钥

前端允许包含 Supabase 项目 URL、publishable key、运行模式和公开真实站点链接。它们不是用户权限凭据。Supabase secret key、旧 `service_role` key、数据库密码、SMTP 凭据、OAuth Client Secret 均只能保留在受信服务端或服务控制台，不得进入 Git 历史、`VITE_*` 变量、构建产物、截图或公开日志。对敏感值设置 `.gitignore` 不能清除既有泄露，发生泄露应撤销或轮换并检查访问记录。依据：[Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys)。

### 5.2 不信任导入和文字内容

题目、样品说明、昵称、退回原因和文字反馈一律按普通文本渲染，不执行 HTML、脚本或配置中的任意代码。导入执行 [06 · 配置与文件格式](06-configuration-format.md) 的大小、结构、范围与数量限制；不执行 Excel 公式、宏或外部链接，也不自动加载文件内引用的网络资源。

导出字符串防止表格公式注入：对可能被表格软件当作公式的文本开头及控制字符按 [06](06-configuration-format.md) 处理；数值列仍输出真正的数值，不能把合法负分数当字符串公式处理。文件名使用受控前缀和标识，不包含未经处理的用户路径。

M2 托管配置应设置必要的安全响应头与限制性的内容安全策略，并只允许实际需要的 API、资源和回调来源。应用不依赖远端脚本任意动态注入；依赖固定版本并提交锁文件。具体头部能力以所选托管平台验证结果为准，不能把一个 HTML 标签等同于所有响应头防护。

### 5.3 审计与脱敏日志

成功的发布、分配、撤销、退回、关闭、归档、账户停用/恢复、导出和分析创建应记录操作人、对象、动作、服务端时间、请求号、数据版本及必要原因。审计不复制评分、文字原文、邮箱、验证码或令牌。被拒绝的请求和系统错误使用脱敏运行日志记录；不要指望已回滚事务中的审计插入仍存在。

导出事件记录授权范围、快照标识、类型和行数，表示“已授权并发起导出”，不等于浏览器最终保存成功；网站不能证明用户已经把文件写入磁盘。账户角色变更和首次管理员初始化也需在受信维护记录中可追溯。

## 6. 隐私最小化与告知

### 6.1 收集范围

| 类别 | 默认处理 |
| --- | --- |
| 邮箱、Auth UUID | 邮箱由 Auth 持有；业务表引用 UUID，不重复复制邮箱到配置、答卷和分析 |
| 昵称、评价员代号 | 使用必要昵称和稳定 `participant_code`；不要求真实姓名、电话、证件、地址或生日 |
| 评分、文字反馈与缺失原因 | 仅用于已告知的实验评价；提示用户不要填写个人敏感信息 |
| 告知接受记录 | 保存版本、关联配置和时间，用于解释当次数据收集范围 |
| 操作记录 | 只保存排错和追溯所需元数据，并纳入保留与删除流程 |

代号可由管理员关联到个人，数据因此是去标识化，**不是匿名数据**。样品编码隐藏名称也只是实验显示策略，不等于无法推断样品身份。提供方可能处理认证、投递和安全日志；隐私告知应写明实际服务提供方和区域，不声称“任何第三方都不接触数据”。GitHub Pages 官方亦说明其为安全目的记录访问者 IP。依据：[GitHub Pages 数据收集说明](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)。

站点告知及每份发布快照至少说明：用途、所收集的数据、谁能访问、管理员联系渠道、实际服务及区域、保留期限与起算方式、退出或申请删除方式、文件下载后的管理责任。尚未提供真实负责人或联系方式时必须标明待配置，M2 不可伪造联系人后宣告可正式收集。

拒绝告知不创建可填写任务权限，也不视为零分。告知版本更新不得静默改写已接受的旧实验记录。本文提供工程控制，不把部署或勾选同意声明为已经完成所有研究伦理或适用规则的审查。

### 6.2 导出与文件处置

真实数据导出仅向当前有效管理员开放，服务端按所选实验与同一分析快照授权返回。默认文件使用 `participant_code`，不包含邮箱或昵称；文本仍可能由填写者带入身份信息，因此下载前提示管理员按用途保管。

文件在客户端临时生成并由用户主动下载，不在业务服务器持久保存导出副本。成功、取消和失败后释放临时对象与大块内存；退出后不恢复上次真实导出的数据缓存。导出文件中记录运行模式、数据范围、生成时间、快照和隐私说明，禁止把示例数据混入真实文件。

下载后的文件不再由网站远程控制。管理员应限制分享对象，并在对应保留期届满或删除请求需要时清理本机和已分发副本。不要承诺停用账号或清空数据库会自动撤回已下载文件。

## 7. 停用、保留与删除

### 7.1 停用与删除是不同操作

账户停用即时阻止新的业务访问，并按数据规范排除其当前分析记录；不会自动删除已有答卷或历史审计。退出登录也不等于注销账户。删除申请通过 `deletion_requests` 或站点公布的联系人受理，核验申请人与数据归属后处理，并告知已完成部分及仍受备份轮换影响的范围。

删除一个实验的数据不得误删同一评价员在其他实验中的记录；删除 Auth 身份前必须处理业务关联，避免孤立记录或误级联。无法继续使用原邮箱的申请走受控人工核验，不通过公开邮箱查询接口透露他人参与情况。停用账户仍需有可用的请求处理渠道。

### 7.2 默认保留策略

以下是本设计的默认值，可对**新发布实验**配置其他明确期限；它不是统一法律期限。策略随 `experiment_versions` 的发布元数据冻结，不能由导入文件任意改变。

- 默认原始业务数据保留至有效采集结束后 `180` 天。
- 有效结束时间取计划截止 `closes_at` 与实际关闭 `closed_at` 中较早的非空值；即使状态仍为 `published`，已经到计划截止也开始计算保留期。
- 未设置计划截止的实验增加 `published_at + 365` 天作为最长采集边界，与提前关闭时间取较早值。到该边界后 RPC 禁止继续保存、提交和退回，站点负责人必须结束并处置该批次；需要延长研究时创建新一轮，不能原地延长冻结快照。
- `retention_due_at` 是有效结束时间加发布时保留天数的派生值，不另设可被任意修改的期限副本。归档、撤销任务、账户停用、重新生成分析或下载文件均不重置期限。
- 无计划截止时，即使尚未手动关闭也不能无限保留；最迟以发布后 `365 + 180` 天作为默认到期界限，若提前关闭则相应提前。

时间计算使用服务端 UTC；界面用实验时区展示。站点负责人应定期查看即将结束和即将到期清单；M2 交付必须包含可执行的处置流程与执行责任，不能因没有后台定时器就忽略这些边界。

### 7.3 到期处理范围

到期或核验后的删除流程覆盖对应草稿、全部提交修订、关联任务中的身份映射、可关联的幂等结果、分析快照的输入与结果、相关临时材料及不再必要的个人资料。应同步更新或作废受影响统计，防止删除原始答案后仍从旧快照恢复个人记录。常规业务记录只留下不能反查个人或回答的清理批次、数量和时间等最小运维证明；恢复备份所需的受限重放清单单独管理。

分析结果不会因为是均值或图表就自动成为匿名数据。V1 不默认永久保留过期实验的聚合结果；若未来需独立保留真正不可识别的统计，须另行确定用途、风险与期限，不把去标识化代号当匿名证明。一般运行日志和删除处理记录也必须有期限，默认最长 `180` 天，不建立无期限身份追踪副本。

备份按实际服务方案和轮换周期处理，不保证在活动数据库删除后立即从所有备份消失。恢复备份时应重新执行已完成的删除清单，避免恢复已删除个人数据；该清单本身只保留执行所需的最小标识并受限访问，保留至所有可能恢复相应数据的备份过期。默认备份轮换和重放窗口也不得超过 `180` 天；确需不同期限时在发布告知与策略中事先明确，不形成隐形的无限期副本。实际备份期限和恢复办法必须进入运维记录。

M2 正式收集前必须完成一次合成数据的到期清理与恢复验证，指定每日检查和到期执行的责任人或调度器。调度未接入时按明确的受信人工流程执行，不宣称已有自动清理任务；如不能提供执行证据，M2 仍属于未完成验收。

## 8. 安全验收与交付证据

详细编号见 [11 · 验收标准](11-acceptance-tests.md)。至少保存以下验证结果，截图和日志均脱敏：

- 两个真实评价员分别登录，在两台设备恢复同一账户的服务端草稿；不存在共享演示数据冒充同步。
- 未登录、`pending_consent`、有效评价员、另一评价员、管理员和 `disabled` 身份直接调用 API，验证允许与拒绝；不只点击网页按钮。
- 修改 `user_metadata`、请求体角色、`user_id`、任务 UUID、配置版本或样品 ID 不能越权；未接受实验告知不能保存或提交。
- 账户停用后继续使用旧 JWT、旧页面和旧幂等键均不能发起新的业务读写；恢复会更新相关数据版本。
- 评价员网络响应不含 `admin_name`、隐藏样品名称、其他人的答案或管理统计；所有真实写入无法通过直接表 DML 绕过 RPC。
- 通过重复提交、同时关闭/撤销、版本冲突和 RPC 中途失败验证事务原子性、幂等与权限检查。
- 在浏览器持久存储、Service Worker 缓存、产物、仓库和日志中检查无真实答卷缓存、验证码及服务端密钥；认证令牌仅处于限定的 SDK 会话存储。
- OTP 发送、过期、限流、退出和服务不可用均使用真实服务结果；断网只保留内存输入，不切换模式或伪造成功。
- 告知接受、保留期、无截止最长采集边界、停用、到期清理、分析快照清除和备份恢复后的删除重放均有合成数据验证记录。

发现服务端密钥泄露、越权读写或真实答卷被公开时，立即停用受影响入口和发布，保全脱敏的排查依据，轮换凭据并修复后重验。不能仅隐藏页面按钮后宣告问题解决。事件处置和回滚步骤见 [09](09-deployment-and-operations.md)。

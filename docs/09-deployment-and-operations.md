## 2. 托管与认证裁决

### 2.1 两条默认部署路径

| 路径 | 前端 | 身份与数据 | 用途 |
| --- | --- | --- | --- |
| M1 `demo` | GitHub Pages | 演示身份、当前浏览器 IndexedDB | 无需外部账号即可完整体验业务闭环 |
| M2 `live` | 适合真实登录应用的独立托管站点 | Supabase 邮箱 OTP、PostgreSQL、受控 RPC 与 RLS | 正式身份、多人共享、跨设备保存和受控数据收集 |

前端使用同一代码库与领域规则，每个部署只装配一种适配器。真实站点可链接到 Pages 演示，演示站点在真实地址已配置且验证后展示“进入真实工作区”；跳转不携带身份令牌、邮箱或答案。默认不建设同一个部署内随时切换数据源的双模式控制台。架构与能力字段见 [03](03-architecture.md)。

Pages 是静态托管，不能执行应用服务端，也不自带共享数据库；浏览器仍可调用外部 API，因此技术上能够连接真实认证。平台边界不只在技术：GitHub 官方不建议 Pages 用于发送密码等敏感交易，也限制以商业交易或商业 SaaS 为主要目的的免费托管。本文不把“使用外部服务”或“改成 OTP”宣称为政策豁免。正式真实系统另选托管环境；Pages 外部 OAuth 试运行见第 7 节。依据：[Pages 概述](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)、[Pages 使用限制](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)。

M2 默认不需要自建完整应用服务器：受控数据库 RPC 可以承载当前业务事务。如果所选托管、认证或后续分析需要受信后端，再配置对应服务。高权限操作和秘密凭据绝不迁到浏览器以省略后端配置。

### 2.2 HTTPS、可见性与项目路径

Pages 项目站点使用 `/questionnaire/` 基路径；Vite 的 `base` 必须为 `/questionnaire/`。HashRouter 使用例如 `/questionnaire/#/tasks` 的地址，避免要求服务器将任意业务路径重写到首页。静态资源、懒加载模块、字体、图片和下载模板都必须遵循构建基路径，不能把 `/assets/...` 错指向域名根目录。依据：[Vite 静态部署](https://vite.dev/guide/static-deploy)、[React Router HashRouter](https://reactrouter.com/api/declarative-routers/HashRouter)。

Pages 支持 HTTPS；发布时核验实际 HTTPS 地址和 Enforce HTTPS 设置，所有外部 API 与资源使用 HTTPS。HTTPS 只保护传输，不替代授权、RLS 或平台适用性判断。来源仓库私有也不代表站点私有；私有 Pages 的访问控制有 Enterprise Cloud 等条件，不能作为本项目默认前提。所有发布文件都按公开互联网资源审查。依据：[Pages HTTPS](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https)、[Pages 可见性](https://docs.github.com/en/pages/getting-started-with-github-pages/changing-the-visibility-of-your-github-pages-site)。

## 3. 构建配置与状态契约

### 3.1 配置表

以下为实施时应建立并验证的配置接口，当前仓库尚无对应构建系统。`.env.example` 只放占位值和说明，真实环境文件加入忽略规则；所有 `VITE_*` 值都按会进入公开产物处理。

| 配置 | `demo` | `live` | 公开性与校验 |
| --- | --- | --- | --- |
| `VITE_APP_MODE` | 必须为 `demo` | 必须为 `live` | 缺失或其他值构建/启动失败，不按请求成败猜模式 |
| Vite `base` | `/questionnaire/` | 使用真实站点实际根路径或子路径 | 编译时检查，逐条验证资源地址 |
| `VITE_SUPABASE_URL` | 不需要、不发真实请求 | 必需 | 合法项目 HTTPS URL |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | 不需要 | 必需 | 仅 publishable key；不得填 secret 或旧 `service_role` key |
| `VITE_LIVE_APP_URL` | 可选 | 不用于选择后端 | 只有已验收真实地址才启用入口，限制为受信 HTTPS URL |
| `VITE_DEMO_APP_URL` | 可不设 | 指向独立 Pages 演示 | 不附带身份或业务数据 |
| 版本信息 | 必需 | 必需 | 源提交、构建标识、模式、契约版本，不含用户或密钥 |

`VITE_LIVE_APP_URL` 与 `VITE_DEMO_APP_URL` 只是公开导航链接，不选择当前部署的适配器，也不会在同一部署内自动切换模式；缺少目标地址时不展示可点击的对应入口。

邮箱模板、SMTP、Auth 限速、Site URL、Redirect URLs、数据库连接、管理员初始化和保留策略在受信配置中维护，不放入公开环境变量。真实 SDK 会话的专用 `storageKey` 与 `sessionStorage` 要求见 [08](08-security-and-privacy.md)。

模式变化必须通过明确发布配置形成新部署；`live` 初始化缺配置或连接失败时显示准确错误，不初始化 IndexedDB 演示身份。缺少外部资源时，可以显式构建 `demo` 并正常发布；这不是运行过程中静默降级。

## 4. 开发分支与本地构建

### 4.1 源代码流程

1. 读取当前仓库规则，获取远端最新 `dev`，检查工作区状态和已有实现。
2. 从 `dev` 创建独立临时 worktree 与功能分支，按 [10 · 实现计划](10-implementation-plan.md) 完成一组可验收任务。不要在 `main` 上实施，也不要清除别人工作区的修改。
3. 更新相应文档、迁移、契约和测试，记录实际安装的 Node、pnpm 与依赖版本。使用一份锁文件，禁止为了安装失败随意更换包管理器。
4. 本地或用户允许的构建环境执行类型、关键契约、浏览器流程及当前里程碑所需数据库检查。测试留痕按仓库当时适用规则保存，不提交真实用户数据。
5. 创建目标为 `dev` 的 PR，说明问题、行为变化、实际模式、验证和外部缺项。按当前授权完成集成；发布产物另进入 `gh-pages`，不修改冷分支 `main`。

### 4.2 命令模板

以下命令是实施后的预期入口，**当前欢迎页仓库没有这些脚本**。T01 应先在 `package.json` 建立相应命令、固定工具版本并生成锁文件；如实际命令采用其他名字，同步本文件和验收文档，不能把模板运行失败误判为产品故障。

```sh
pnpm install --frozen-lockfile
pnpm typecheck
pnpm test --run
```

发布 Pages 演示时使用明确的演示构建入口：

```sh
pnpm build:demo
pnpm preview
```

真实公开配置已就绪时，另行构建和预览真实站点：

```sh
pnpm build:live
pnpm preview
```

两种构建不能混作一份产物，记录并发布对应模式的输出。浏览器端到端与数据库权限测试需另建立清晰入口并记录执行结果，不能只凭构建成功宣布业务通过。构建命令应校验本次环境的 `VITE_APP_MODE`、Vite `base` 和必要公开配置；不在命令行回显秘密凭据。默认产物目录为 `dist/`，演示构建的本地预览必须实际访问 `/questionnaire/` 及其 hash 深链接，而不只看开发服务器根路径。

M1 验证至少完成建实验、导入、发布、分配、评价员填写、草稿恢复、提交、退回、描述统计与下载。M2 另执行真实认证、双用户越权、双设备恢复、事务冲突、停用、告知和保留期测试。具体门槛见 [11](11-acceptance-tests.md)，不为可逆的文案调整重复运行无关的整套测试。

## 5. GitHub Pages 发布 M1

### 5.1 构建产物与发布源

采用**本地构建、分支发布**：

1. 从已经验证的源提交生成显式 `demo` 构建，确认没有真实 API 调用或真实数据。
2. 在隔离的发布目录或 `gh-pages` worktree 中整理 `dist/` 的内容。将 `index.html`、`assets/` 等放在发布分支根目录，不额外套一层 `dist`；根目录包含 `.nojekyll`。
3. 检查静态产物：只含网站所需公开资源、人工示例和不敏感版本信息；不含环境文件、数据库导出、SMTP/OAuth 凭据或真实名单、答案、分析输入。
4. 将产物作为可追溯提交推送到 `gh-pages`。保留源提交与产物提交的对应记录，正常保留发布历史，不以覆盖 `main` 或强制重写所有历史作为默认方案。
5. 在 Settings → Pages 核验当前值，设置 `Deploy from a branch`、`gh-pages`、`/(root)`。这是未来交付操作，本轮尚未执行。
6. 查看 GitHub 生成的发布结果，打开实际站点进行第 8 节的线上复验；只看到推送成功不等于网站部署成功。

Pages 分支发布源只支持所选分支的根目录或 `/docs`，不能直接选择任意 `/dist` 目录。`.nojekyll` 用于跳过 Jekyll 构建，不是关闭全部发布机制。依据：[配置 Pages 发布源](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)。

### 5.2 GitHub-hosted Runner 的边界

本项目不新增使用 GitHub-hosted Runner 安装依赖、运行测试或构建产品的自定义工作流，也不把 GitHub-hosted Runner 配额作为应用构建依赖。构建在本地或既有允许的环境完成。

GitHub 官方说明，即使通过外部构建工具提交静态产物，Pages 自身仍使用 GitHub 管理的 Actions workflow 完成托管侧部署。因此本方案不能称为“完全零 Actions”。本设计将这一内置流程视为选择 GitHub Pages 后的正常发布组成，不为它重复设置额外确认环节；它与新增产品构建 workflow 是不同事项。依据：[配置 Pages 发布源](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site)。

如果未来出现明确禁止任何托管侧 Actions 的新约束，应重新选择托管方案，不能宣称 `.nojekyll` 或本地构建已消除这一机制。不要为规避措辞而未经安排创建自托管 Runner、付费机器或新的外部账号。

## 6. M2 真实环境接入与上线

### 6.1 外部资源清单

| 资源 | 所有者需提供或授权配置的内容 | 验收证据 |
| --- | --- | --- |
| Supabase 项目 | 所属账户、项目、区域、实际计划、公开 URL 与 publishable key | 项目可达，选定版本与限制已记录 |
| 数据库管理入口 | 运行版本化迁移的受信权限 | 表、约束、RPC、最小 grants、RLS 及迁移版本可核对 |
| 自定义 SMTP | 发信服务账户、发信地址、凭据、域名验证和实际限额 | 非项目团队的受控测试邮箱能够收到 OTP |
| 真实前端托管 | 用户已有或明确安排的托管项目、默认域名或自有域名 | HTTPS、实际基路径、安全配置和公开站点可验证 |
| Auth 配置 | 邮箱模板、OTP 有效期、服务端限速、Site URL 与准确 Redirect URLs | 注册、登录、过期、重发与退出按预期工作 |
| 管理员 | 已验证并建档的真实用户 UUID、可信授予方法 | 普通新用户仍是评价员，管理权限可审计 |
| 隐私与运维 | 负责人、联系渠道、服务区域、告知版本、保留规则、备份及清理责任 | 已完成合成数据处置与恢复验证 |

上述资源未提供时不自行购买、开通付费计划、注册域名或借用不明确归属的项目。先完成可交付代码、迁移、配置模板、验证入口与演示发布，再报告具体缺项和接入方式；不要只说“需要后端”后停止。公开 URL/key 与秘密管理凭据分开说明，秘密通过受信渠道配置，不要求贴入仓库或公开聊天记录。

不能承诺免费额度、不会休眠、无限邮件或固定可用性。Supabase 官方生产清单说明低活跃免费项目可能暂停，并建议自有 SMTP；备份与恢复能力取决于实际方案。实施时重新核对计划和限制，不以旧价格或试用行为作长期承诺。依据：[Supabase Production Checklist](https://supabase.com/docs/guides/deployment/going-into-prod)。

### 6.2 实施顺序

1. **准备隔离验证环境。** 使用人工构造数据，记录项目归属、区域和配置。数据库迁移进入版本控制；敏感凭据只进入受信环境。
2. **部署数据约束。** 建立 [04](04-data-model.md) 的实体、不可变发布与修订、索引和状态约束，部署 [05](05-api-contracts.md) 的 RPC、RLS 和明确执行权限。按 [08](08-security-and-privacy.md) 检查安全函数。
3. **配置真实认证。** 使用邮箱 OTP 模板与自定义 SMTP。Site URL 使用真实站点完整地址，允许跳转只列准确需要的地址；开发地址与正式地址区分。生产不用覆盖任意域名或路径的宽泛通配。依据：[Supabase Redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls)。
4. **建立初始账户。** 测试新身份默认 `participant + pending_consent`，完成站点建档后 `active`，再通过受信维护将指定 UUID 授为管理员。接受实验告知之前不能保存或提交。
5. **部署显式 live 构建。** 用同一源版本配置真实 URL 与 publishable key、准确 `base`；会话使用 SDK 专用 `sessionStorage`，业务草稿不持久缓存在浏览器。真实站点不加载或播种演示数据库。
6. **执行端到端与越权验证。** 用真实 Auth 会话直接调用 API，同时验证双设备恢复、角色即时检查、服务端时间、事务、幂等和参与端投影。失败时保留为未验收状态。
7. **执行运维演练。** 验证停用、到期停止采集、清理全部原始与分析副本、备份恢复后的删除重放。确认执行者或调度器实际可用，不假定 cron 已存在。
8. **开放真实入口。** 通过验收后更新公开真实工作区链接、状态说明和交付记录。演示站点继续可用，不导入真实身份与答案。

M2 默认 OTP 不需要 OAuth 应用，也不需要额外实现 OAuth 回调页面。不能把可选第三方登录的配置缺项当成默认 M2 的阻塞条件。

### 6.3 资源缺失时的准确交付

交付报告逐项区分“代码已实现”“外部已配置”“集成已验证”。例如 SMTP 缺失时，应报告真实认证代码和模板已具备、无法验证向真实评价员发信、当前线上为 demo，而不是宣称真实注册已完成。

缺项须写明名称、用途、需要的权限、已完成工作和剩余验证。例如“缺少属于本站的 SMTP 配置，阻塞外部邮箱 OTP 投递验证”，比“后端还要配置”更可执行。可提供现有托管的接入选项，但不在未有资源时承诺最终域名或新增服务成本。

## 7. 可选：Pages 上外部 OAuth 非敏感试运行

本节不是 M1/M2 默认验收项。只有在确认实际用途、GitHub 适用边界和身份提供方条件后，才考虑让 Pages 前端通过 Supabase 重定向到外部提供方。密码由提供方页面接收，Pages 页面不显示本站密码框；这仍不能消除访问令牌、邮箱和业务数据的敏感性，也不是官方明确给出的政策豁免。

如实施该试运行，使用下列约束：

- 持续标明真实服务试运行和仅限非敏感测试数据；不把它包装成默认生产认证完成。
- 选择提供方后创建其 OAuth 应用，把 Client Secret 保存在 Supabase 提供方设置；Google 接入还需要 Cloud 项目、同意界面和提供方允许的回调。依据：[Supabase Google 登录](https://supabase.com/docs/guides/auth/social-login/auth-google)。
- 使用 PKCE。回调到实际存在的站点根地址，例如 `https://siliconyc.github.io/questionnaire/`，在 HashRouter 启动前处理查询参数中的授权 code，交换成功后清理地址，再进入站内目标。
- 返回目标只能是受控站内路由，不接受任意外部 `returnTo`。错误、取消、过期和重复回调不得产生半登录状态或泄露完整参数。
- 不使用不存在的 `/auth/callback` 服务器路由，也不让隐式流的 token fragment 与 `#/...` 路由竞争同一个 hash。PKCE 的 verifier 需要与发起流程一致的浏览器和设备；跨设备点击认证链接应有可理解的失败与重新开始入口。依据：[PKCE flow](https://supabase.com/docs/guides/auth/sessions/pkce-flow)、[Implicit flow](https://supabase.com/docs/guides/auth/sessions/implicit-flow)。
- 同样执行 [08](08-security-and-privacy.md) 的存储、RLS、RPC、停用与隐私要求；不得因称作试运行而开放角色表或直接写入权限。

不能把此选项作为逃避默认邮箱 OTP、真实应用托管或完整权限验收的捷径。没有安排该选项时，前端不需要提供一个不可用的 Google 登录按钮。

## 8. 上线复验与发布记录

每次发布保留一份不含秘密或真实答卷的记录，至少包括源提交、构建工具版本、依赖锁文件、构建时间、模式、产物提交/版本、前端地址、数据库迁移与接口版本、已执行验证、已知缺项和回滚版本。界面的版本信息能与记录对应。

### 8.1 Pages 线上复验

- 从 `/questionnaire/` 首次打开，页面和资源加载正常，浏览器没有指向错误根路径的请求。
- 复制 hash 深链接到新标签页并刷新；未登录、无权限和未知路由的入口可用，不产生静态服务器 404。
- 普通浏览器完成演示操作，刷新后恢复；换一个浏览器看到独立示例数据，并有清楚说明。
- 手机尺寸与桌面上完成填写、提交和文件下载；图表数值与导出一致。
- 进入开发者网络和存储检查，M1 不调用真实 Auth、不发送真实邮件、不携带真实数据；进阶能力与实际实现一致。

### 8.2 M2 线上复验

- 使用经允许的测试邮箱完成真实 OTP；两个真实用户及两个设备验证共享、隔离和草稿恢复。
- 直接 API 验证普通身份不能访问他人任务、隐藏字段或统计，不能授予自己管理员；新建档和实验告知的门槛真实生效。
- 用尚未过期的会话验证账户停用即时阻止新请求；管理员提交也必须有本人任务，不能以管理权限代填。
- 断网、Auth 失效、服务异常与并发冲突不产生假回执、不清空内存输入、不切换 demo。
- 检查产物无服务端秘密，浏览器无真实答卷持久缓存；实际退出、保留期、导出释放与清理行为符合 [08](08-security-and-privacy.md)。
- 备份、恢复和到期处理已有执行证据；真实隐私联系人、服务区域和告知版本已配置。

只有线上地址和完整里程碑验证均通过，才能报告该里程碑已上线。仅有源码、截图、成功构建或部署任务绿灯，都不能单独证明完整业务可用。

## 9. 备份、到期处理和运行检查

| 责任 | 日常工作 | 所需证据 |
| --- | --- | --- |
| 站点维护者 | 发布、前后端版本兼容、依赖和服务告警 | 发布记录、错误摘要、回滚依据 |
| 服务所有者 | 项目状态、邮箱投递、配额、计费与备份可用性 | 实际服务配置与恢复演练记录 |
| 实验管理员 | 告知、分配、关闭、账户停用和导出管理 | 业务审计、待办处置结果 |
| 数据处置负责人 | 每日检查采集到期与保留到期，执行受控清理 | 到期清单、清理批次与备份删除重放记录 |

角色可由同一人承担，但上线记录不能只写“系统自动处理”。按 [08](08-security-and-privacy.md)，默认有效结束后保留 `180` 天；无截止实验最迟发布 `365` 天后停止采集。保存答卷、提交、退回及任务恢复的 RPC 每次检查采集边界，不依赖定时改状态；关闭、归档等管理操作按各自状态规则执行。物理清理由实际部署的受信程序执行。没有调度器时明确采用人工受信流程并记录执行，不虚构已有自动任务。

M2 上线前确认可恢复备份的实际能力、频率、保存位置、访问权限与轮换周期，记录可接受的数据丢失窗口和恢复目标。不得把同一数据库里的一张复制表当成独立备份，也不将数据库导出提交到 Git 或 Pages。备份使用受限且适合敏感数据的位置；验证恢复包括配置快照、修订、任务关联、授权和删除清单。

定期用合成数据复验恢复；真正恢复时先限制写入，确认恢复时间点，再重新执行已处理的删除请求，避免恢复已删除数据。导出文件在客户端生成，服务端不长期保留下载副本；真实用户自行下载的文件按隐私告知和管理员流程另行清理。

运行日志只收集请求标识、操作、状态、耗时和脱敏错误。监控 OTP 失败、RPC 错误、异常权限拒绝、项目暂停、空间或额度接近限制及清理失败；不要为排错开启记录完整认证头、邮箱、文字答案和 SQL 参数的公开日志。

## 10. 回滚与故障处理

### 10.1 回滚原则

前端回滚采用已验证产物形成新的发布提交，保留原有版本对应关系；不通过强制重写 `main` 解决发布问题。回滚前确认旧前端与当前 RPC/Schema 兼容，不能把已修复的权限漏洞重新上线。

数据库迁移以可审查的增量变化维护。涉及破坏性迁移时，在实施前明确兼容窗口、备份和恢复方案；不要在故障中盲目执行反向迁移或删除新列。必要时暂停写入，保留可读错误说明，再由受信维护恢复。旧客户端不兼容时明确要求刷新，并阻止不可靠的写入。

M1 的 IndexedDB 版本也需要迁移说明。旧前端不能读取新 Schema 时提示版本问题，不自动清库伪装修复；只有用户明确执行“重置演示”才清除其演示数据。

### 10.2 常见故障

| 现象 | 优先检查 | 必须保持的行为 |
| --- | --- | --- |
| 页面空白或资源 404 | Vite `base`、发布根目录、资源引用与发布状态 | 不以改域名根路径掩盖项目路径问题 |
| 深链接刷新 404 | 是否使用 hash 路由、链接是否误写为服务器业务路径 | 返回真实可达入口，不添加未部署的后端路由 |
| OTP 只向项目成员送达 | 是否仍使用默认 SMTP、发信域名是否验证 | 报告邮件服务待配置，不直接把用户标为已验证 |
| OTP 延迟或限流 | Auth 限速、发信商配额、退信与反滥用设置 | 提示等待和重试，不保存验证码到日志 |
| 登录后无权限 | 建档与实验告知、角色表、账户状态、grants/RLS/RPC 版本 | 不暂时开放全表权限“修好登录” |
| 数据服务不可达 | 项目暂停、网络、服务故障、配置是否指向正确项目 | 保留内存输入，暂停真实写入，不切换 demo |
| 提交超时或重试 | 是否使用同一幂等键、服务端是否已返回可查询回执 | 不生成第二份提交，不凭前端时间猜成功 |
| 另一设备有新草稿 | `edit_version` 与最新服务端版本 | 展示冲突，由用户决定后重新提交 |
| 演示存储失败 | IndexedDB 权限、配额、浏览器隐私设置 | 显示无法保存，提供明确导出或重试，不假报持久化 |
| 备份或到期清理失败 | 权限、任务实际执行、范围和关联约束 | 记录并处理异常，不能仅更新“已清理”状态 |

如发生密钥泄露或越权，先停用受影响入口、限制进一步访问，轮换或撤销凭据并核查影响范围；修复后重做真实拒绝测试，再恢复发布。前端隐藏按钮或切换到演示不能代替修复与事件说明。

## 11. 最终交付清单

每个里程碑的交付报告都应包含可访问地址、源提交、实际运行模式、逐模块完成状态、验证结果、运维责任和剩余外部配置。M1 必须能完整操作；M2 必须有真实服务与数据隔离证据；M3 按 [07 · 统计分析](07-statistical-analysis.md) 单独验收。

交付时同步根 README 的真实启动、构建、分支与发布说明，不继续保留“当前仅欢迎页”或旧发布源作为现状。当前文档阶段只记录这一未来更新要求，不提前改写实际实现状态。
